# CLAUDE.md

Générateur de CV local, lisible par les ATS, avec un serveur MCP. **`CAHIER_DES_CHARGES.md` fait foi** ; on avance lot par lot (§13), et tout choix structurant fait l'objet d'un ADR dans `docs/decisions/`. Si le cahier est muet : l'option la plus simple qui respecte les règles ATS, notée dans un ADR. Si un point invalide le cahier : proposer une correction, ne jamais dévier en silence.

## Commandes

```bash
npm install              # versions figées ; postinstall compile le MCP ; prepare installe le hook
npm run dev              # API (127.0.0.1:4311) + interface (127.0.0.1:4310) sur data/
npm run dev:demo         # idem sur une copie de la fixture fictive « courte »
npm test                 # Vitest (pretest recompile apps/mcp pour le test en sous-processus)
npm run test:ats         # batterie ATS §12.2 : ats-classique et visuel, CV et lettre, FR/en-GB/en-US, 3 polices (Poppler requis, sinon ATS_SINGLE_EXTRACTOR=1)
npm run test:recette     # scénarios T-01 à T-08 (§12.6) ; rapport de recette : docs/recette.md
npm run typecheck        # tsc strict partout (packages, apps, scripts, web)
npm run lint             # ESLint
npm run format           # Prettier
npm run build:mcp        # recompile apps/mcp/dist (puis /mcp pour reconnecter)
npm run data:init        # data/ vide et valide
npm run import:linkedin  # import LinkedIn en propositions (-- <fichier>, --dry-run) : sur data/, à lancer par l'utilisateur seulement
npm run build && npm start  # mode production : interface + API sur 127.0.0.1:4310 (CV_PUBLIC_ORIGIN : instance en ligne, connexion par clé)
npm run deploy           # déploie HEAD sur le VPS (ADR 0018) : une connexion SSH, l'utilisateur touche sa YubiKey ; outillage privé
```

Avant un commit : `npm run typecheck`, `npm run lint`, `npm test`, et `npm run test:ats` si le rendu ou le contrôle ATS a changé.

## Dépôt public

- Le dépôt est public. Ne jamais versionner `scripts/vps/`, `scripts/deploy-vps.ts`, `.mcp.json` ni `docs/prive/` (ignorés par git, refusés par `guard-commit`) : ils décrivent le serveur et l'accès de l'auteur. Aucun chemin local (`C:\Users\…`), chemin du serveur, hôte SSH, nom de clé ni faiblesse du serveur dans un fichier versionné ; `.mcp.json.example` sert de modèle.

## Règle des données réelles

- Les données réelles (`data/`, `import/`, ou `CV_DATA_DIR`) ne se lisent **que par les outils `mcp__cv__*`**. Ne jamais les lire, les copier ni les afficher autrement (les règles deny de `.claude/settings.json` ne couvrent pas un script lancé par Bash).
- Le développement et les tests se font **sur `fixtures/`** (personas fictives, et `fixtures/imports/` : export LinkedIn et CV fictifs, régénérés par `npx tsx scripts/make-fixture-imports.ts`). Aucune donnée réelle dans le dépôt ni dans les fixtures.
- `npm run import:linkedin` et le mode `dryRun` d'`import_linkedin` sur l'export réel ne se lancent **qu'avec l'accord explicite** de l'utilisateur (le script écrit dans `data/`) ; Claude n'appelle jamais le script par Bash sur les données réelles.
- Après une modification d'une persona, mettre à jour son `ids.json` (et, pour `courte`, les empreintes de `fixtures/proposals/`, ADR 0010, et la couverture attendue de `fixtures/analyses/` dans `packages/core/test/coverage.test.ts`, ADR 0013).

## Règles ATS non négociables

- Rendu PDF **uniquement** par Typst (`@myriaddreamin/typst-ts-node-compiler` 0.7.0, Typst 0.14.2). **html2pdf.js et html2canvas sont interdits** (ESLint les refuse), comme toute impression navigateur.
- Réglages obligatoires des gabarits ATS : `set text(font: <police du thème>, fallback: false, lang: …, hyphenate: false, ligatures: false, tracking: 0pt)`, `set smartquote(enabled: false)`, `set par(justify: false)`, `set document(title: …, author: …, date: none)`, marges ≥ 1,5 cm, corps ≥ 10 pt, aucun texte < 9 pt.
- **Aucun texte écrit en dur** dans un `.typ`, même une ponctuation : tout vient de la projection (`core.project()`). Aucune interpolation de texte utilisateur dans le source Typst, aucun `eval()`.
- Ni `grid`, ni `table`, ni `hide`, ni texte blanc ; `place()` seulement dans `photo()`, qui ne contient que `place(top + right, image(…))`, et aucune `image()` hors de `photo()` (T-ATS-17 le vérifie, règle `image-outside-photo`). Blocs `box` pour les dates, chaque coordonnée, chaque terme protégé, chaque mot composé.
- Modèle `visuel` (ADR 0017 et 0019, repris du CV de l'utilisateur) : bandeau (photo ronde, nom, titre), puis colonne latérale **à gauche** (coordonnées, puis sections `side`) et colonne principale ; texte extrait dans l'ordre visuel (bandeau, gauche, principale) ; « destiné à une lecture humaine, déconseillé pour les portails ATS ». Mêmes réglages et même règle « aucun texte en dur » ; le linter lui applique le profil `visuel` (choisi par le **nom** du gabarit, `lintProfileOf`) : `grid` permis, `photo()` peut découper l'image en cercle (`box`, `clip`, `radius`, `height`), `link-icon()` dessine l'icône d'un lien (une image seule, `data.icons.at(i.kind)` et `alt: i.alt`, règle `icon-content`, ADR 0025) ; dans les deux profils, l'image de `photo()` porte son `alt` (projection, jamais visible) ; tout le reste (texte en dur, `eval`, `hide`, `table`, texte blanc, < 9 pt, `place` hors de `photo()`) reste bloquant. Ne jamais affaiblir le profil `ats` (ats-classique, lettre). Colonne Visuel du contrôle : `toVisualColumn` (T-ATS-05 à 08 orange, 15 et 16 sans objet) et `report.notice`. La projection range les sections de la colonne latérale (`side`) ; la couleur d'un texte doit atteindre 4,5:1 sur son fond (`sidebarTint`). Jamais de rangée `1fr` dans la grille : elle ne se coupe pas entre deux pages et tronquerait un CV trop long ; la teinte s'arrête avec le contenu (ADR 0020).
- L'image de la photo passe par `mapShadow` (chemin POSIX sous le workspace), jamais par la projection. Dans le DOCX : `ImageRun` en ligne, jamais flottante ni dans un en-tête.
- Liens (ADR 0025) : chaque lien de l'identité a un `style` (`url` par défaut, `name`, `icon`) et un `name` bilingue facultatif (sinon `labels.linkNames`). L'URL reste toujours en clair (ATS-10). L'icône (`ProjectedContact.icon`) n'existe que dans le visuel : en `ats-classique` et dans le DOCX, l'URL seule (ATS-08, T-DOCX-01). Les SVG (`packages/render/src/icons.ts`, sans texte, à la couleur d'accent) passent par `mapShadow` comme la photo.
- Une seule colonne (sauf le visuel), intitulés standard (§5.3), 1 page stricte, polices du thème uniquement : Carlito, Source Sans 3, IBM Plex Sans, TTF statiques OFL de `packages/render/fonts/` (SHA-256 dans les ADR 0007 et 0017, vérifiés par `fonts.test.ts`). Une nouvelle police = un ADR, ses SHA-256, le contrôle des glyphes des trois personas, T-ATS-09, et T-ATS-03 avec `pdftotext` (espace trop étroit : mots collés par Poppler ; `wordSpacing` du thème, 125 % pour Source Sans 3). Accent : contraste ≥ 4,5:1 sur blanc (`accentProblem`, message avec le ratio). DOCX : Carlito déclarée « Calibri » ; une police sans équivalent métrique aussi, avec T-DOCX-03 orange.
- Design (ADR 0020, batterie T-DES de `reports/`) : pas de ligne de 1,25 (normale) ou 1,20 (compacte) du corps, `leading` calculé par police (`THEME_FONT_META.capHeight`), jamais sous 120 % ; échelle verticale ligne < entrée (`entryGap`) < section (`sectionGap`), la première entrée d'une section collée à son intertitre ; dates sur la dernière ligne de l'intitulé si elles y tiennent, sinon seules à la ligne suivante, toujours au bord droit (`title-line`, mesure par `layout`) ; `par.linebreaks` vient de la projection et `text.costs.runt` vaut 100 000 % (aucune ligne creuse) ; un tiret séparateur reste avec le mot précédent (`segmentText`), le « | » des coordonnées d'`ats-classique` avec la coordonnée précédente. Les tests de `visual.test.ts` vérifient ces propriétés sur le PDF.
- T-ATS-17 (analyse statique) et `npm run test:ats` doivent rester au vert.
- On parle de **lisibilité** ATS, jamais de « passer l'ATS ».

## Conventions

- **Identifiants et commentaires du code en anglais** ; **interface, messages et documentation en français**.
- TypeScript strict, ESM, npm workspaces. Versions **exactes** ; `--legacy-peer-deps` interdit ; une montée de version = un ADR.
- Serveur MCP : **stdout réservé au protocole**. Pas de `console.log` dans `apps/mcp` ni `packages/*` (`console.error` ou `log()` vers stderr). Racine résolue par `CV_ROOT` / `CLAUDE_PROJECT_DIR` / chemin du module, jamais `process.cwd()`.
- Aucun outil MCP ne supprime ni n'écrase le contenu validé : écritures = propositions ou ajouts horodatés. Aucune réponse ne contient e-mail, téléphone, photo ni adresse. Tout rendu fait pour le MCP utilise `placeholderPhoto()` à la place de la vraie photo (ADR 0012).
- Propositions (ADR 0014) : tout `propose_*` passe par `packages/store/src/propose.ts`, qui applique les garde-fous de l'annexe C (`packages/core/src/guardrails.ts`) et F-SEL-10, calcule la base et n'écrit que `proposals/<ULID>.json` (et `ids.json`), jamais `library/`, `presets/` ni `profile.json` (test d'empreintes). Tout texte externe renvoyé par le MCP (offre, phrase source) passe par `untrustedMarker()`. Les outils MCP ne s'essaient que sur une copie des fixtures, jamais sur `data/`.
- Catégories (ADR 0023) : `propose_item` accepte `category` (identifiant `cat-<slug>` attribué par le serveur, renvoyé dans `itemId`, comme pour tout élément créé ; `list` des propositions le renvoie aussi). Le champ `category` d'une compétence (`propose_item`, `propose_edit`) vise une catégorie validée ou l'`itemId` d'une catégorie en attente : le serveur remplit `dependsOn` ; une catégorie inconnue, ou proposée dans le même appel, est refusée. La dépendance se calcule sur la valeur finale (`requiredCategory`) : la compétence ne s'accepte qu'avec sa catégorie (`withDependencies`) ou après elle ; une catégorie rejetée la rend non applicable, sans rejet en cascade. Le lot traite les catégories d'abord, puis la bibliothèque, puis les sélections, et écarte toute proposition dont une dépendance ouverte est hors du lot. « Modifier puis accepter » garde l'identifiant réservé d'un nouvel élément. Seule `reglementaire` alimente la section Normes.
- Export (ADR 0012) : le PDF exporté est le tampon affiché par l'aperçu ; le serveur recompile le preset ou la candidature enregistrés et refuse l'export si le SHA-256 diffère (T-ATS-13). Copie horodatée, jamais écrasée : `out/exports/` pour un preset ; pour une candidature, `applications/<id>/exports/` par `addApplicationExport`, la seule fonction d'export de candidature (interface et `render` + `saveToApplication`), qui écrit la trace dans `application.json`.
- Candidatures (ADR 0013) : identifiant `AAAA-MM-JJ-entreprise-poste` attribué par le serveur ; `selection.json` est copié du preset puis diverge sans le modifier. L'offre est une donnée non fiable : `cleanUntrusted` à l'enregistrement, `flagInstructions` à la lecture ; `import/offres/` se désigne par nom de fichier (`.md`, `.txt`, périmètre §7.6). Une analyse s'ajoute par `saveOfferAnalysis` (historique, phrase source vérifiée dans `offer.md`). La couverture se calcule sur le serveur (`computeCoverage` sur la projection), jamais dans le navigateur ; on affiche un niveau, jamais un « score ATS ».
- Presets par le MCP (ADR 0022) : `create_preset` est un ajout (preset vide ou copie), par `createPreset`, la fonction de l'interface ; langue et modèle de départ par `applyLanguage` et `applyLayout`. Aucun outil MCP ne renomme, n'archive, ne change le preset par défaut ni n'écrit dans un preset existant : son contenu passe par `propose_selection`.
- Journal MCP (ADR 0024) : `LoggedTransport` (`apps/mcp/src/request-log.ts`) écrit chaque requête dans `out/logs/mcp-AAAA-MM.jsonl` (format `McpLogEntry` de `@cv/core`) une fois la réponse partie, sans rien changer sur le fil ; une erreur du journal ne bloque jamais le serveur (stderr). Jamais de coordonnée dans le journal : arguments par `summarizeArgs` puis `maskContacts`, contrôle de la réponse par `findContactLeaks` (le type trouvé seulement). Lu par `GET /api/mcp-log` et l'écran « Journal MCP », jamais par un outil MCP. Un test qui lance le serveur compilé passe un `CV_OUT_DIR` temporaire (sinon il écrit dans le `out/` du projet). Le journal réel (`out/logs/`) se consulte dans l'interface, comme les données réelles.
- Thème et modèle (ADR 0017) : `template` d'un preset ou d'une candidature (`selection.json`) ; `applyLayout` (`@cv/core/selection`) met `own-section` en entrant dans le visuel et `skills-subgroup` en en sortant, ne coche jamais la photo ; `renderCv` l'applique aussi à un `layout` forcé (MCP). La lettre prend la police et l'accent de la candidature (gabarit unique).
- Propositions : une reformulation acceptée devient une nouvelle variante, une traduction ne remplit qu'une langue vide ; `stale` est calculé à la lecture, jamais écrit (ADR 0010).
- Imports (ADR 0015) : l'import LinkedIn (`packages/store/src/linkedin.ts`, lecture pure dans `packages/core/src/linkedin.ts`) est **une** fonction partagée par l'interface, le script et `import_linkedin` ; il passe par `proposeImported`, qui partage avec `propose_item` le dédoublonnage (bibliothèque, propositions en attente, même envoi), les garde-fous et l'écriture. Un doublon d'un élément validé devient un complément (`item` avec `duplicateOf` : seules les puces nouvelles s'ajoutent), une puce proche une `variant`, une nouvelle forme d'une compétence un `alias` ; un doublon d'une proposition en attente renvoie `duplicateOf` sans rien créer. Le ZIP est lu en mémoire (CSV attendus du premier niveau, 20 Mo au plus) ; Birth Date, Address, Zip Code et Maiden Name ne sont jamais lus ; l'identité trouvée ne sort jamais par le MCP (préremplissage dans l'interface seulement). Une date illisible garde l'année et un contrôle `date-to-verify`, qui exclut la proposition de l'acceptation en lot (`batchExclusion`). Le texte d'un PDF ou DOCX de `import/` vient de `extractImportText` (render), transmis au store par le MCP.
- Dépôts d'un projet (ADR 0027) : `repos`, liste de liens `{url, display}` après le lien principal `url` ; le schéma refuse un dépôt en double ou égal à `url` (`linkKey`). Le sous-titre se construit segment par segment (chaque URL son bloc et son lien, le séparateur hors du lien). Un projet est le doublon d'un autre par son nom ou par un lien commun ; ses dépôts nouveaux passent par `propose_edit` de `repos` (liste complète). L'import se fait par le skill `ajouter-depots-github` : Claude lit GitHub, le serveur ne fait aucun appel réseau (NF-02).
- Lettre (ADR 0016) : versions `letters/<fr|en>/v<n>.json` créées par `createLetterVersion` (numéro sous le verrou, `DataStore.create` exclusif : jamais d'écrasement) ; la version active et le statut finale (irréversible) ne changent que dans l'interface, jamais par le MCP ; seule la version active s'exporte (`resolveLetterTarget`, `NO_ACTIVE_LETTER`). Claude n'écrit que les paragraphes avec un rôle (ordre `checkLetterRoles`) ; expéditeur, date du jour, objet, formules et « P. J. » viennent de `projectLetter`. Les garde-fous de la lettre (`checkLetter`) sont des avertissements calculés à la lecture ; seuls les `sourceIds` inconnus sont refusés. Gabarit unique `lettre.typ`, mêmes règles que les gabarits ATS ; export dans `exports/<…>_lettre/` par `addApplicationExport` (`kind: 'letter'`).
- Anglais (§5.4, ADR 0015) : l'orthographe de la variante (`text/en-spelling.ts`) est un avertissement `SPELLING_VARIANT`, jamais un blocage ni un critère ATS ; en en-US, la ligne du permis est générée (`US_DRIVING_LICENSE`). Le motif `UNTRANSLATED` porte la liste complète des champs (`fields`), chacun avec son correctif. Toute écriture de l'API renvoie `writes: [{file, revision}]` pour que l'interface ignore ses propres événements SSE (ADR 0009).
- `packages/core/src/selection-ops.ts` (`@cv/core/selection`, ADR 0011) , `packages/core/src/export.ts` (`@cv/core/export` : nommage, motifs de blocage, texte normalisé, ADR 0012) et `packages/core/src/offer.ts` (`@cv/core/offer` : nettoyage et signalement de l'offre, types et seuils de la couverture, ADR 0013) sont importés par le navigateur : ils ne doivent importer **que des types** et des modules sans Zod. L'interface garde son état dans Zustand + Immer ; le preset s'enregistre seul, avec sa révision ; une candidature ouverte est éditée comme un « preset virtuel » (`virtualPreset`).
- Texte stocké = sortie de `sanitize()` (annexe B.1) ; le schéma refuse le reste. Les caractères invisibles s'écrivent en échappements `\uXXXX` dans le code.
- Windows d'abord : le chemin du projet contient une espace (toujours entre guillemets) ; `path` côté Node, chemins POSIX côté Typst.

## Instance en ligne (ADR 0018)

- **Accès au VPS seulement par la YubiKey** : prévenir l'utilisateur avant chaque connexion SSH (il touche la clé), par l'hôte et la clé dédiés décrits dans `docs/prive/exploitation-vps.md` (ignoré par git ; OpenSSH de Windows) ; jamais avec une autre clé ni un mot de passe. Ne jamais lire un fichier de clé privée. Aucun code d'enregistrement ni OTP ne transite par Claude : l'utilisateur lance `auth-code.sh` lui-même.
- Les données réelles du serveur (`CV_DATA_DIR`, `CV_IMPORT_DIR`) obéissent à la même règle : outils `mcp__cv__*` seulement ; `receive-data.sh` est lancé par l'utilisateur. Claude ne copie jamais `data/` ni `import/`.
- NF-01 : écoute sur `127.0.0.1` seulement ; une origine publique (`CV_PUBLIC_ORIGIN`) exige la connexion par clé, et réciproquement (`createApp` refuse sinon). Ne jamais affaiblir `security()` ni `PasskeyAuth.gate()` ; les clés (`CV_AUTH_DIR`, `auth/`) restent hors de `data/`, du ZIP et du MCP.
- `npm run deploy` déploie le **dernier commit** (`git archive HEAD`) ; une modification du MCP ou du serveur ne prend effet sur le VPS qu'après déploiement, puis `/mcp` pour reconnecter.
- Relais à la demande (ADR 0026) : `.mcp.json` et Claude Desktop lancent `node apps/mcp/dist/relay.js` suivi de la commande SSH. Le relais répond seul au démarrage (`initialize`, listes, `ping`) avec la copie `out/mcp-relay/<empreinte>.json` (descriptions seulement, jamais une donnée) et n'ouvre SSH (la YubiKey) qu'au premier outil ou prompt ; sans copie, dès `initialize`. Il ne dépend que de `node:*` et de `root.ts`, et ne garde aucune connexion d'une session à l'autre.
- Commande SSH du MCP (`.mcp.json`, Claude Desktop, après le relais) : `sudo -n -u cv env CV_SSH_CONNECTION="$SSH_CONNECTION" sh …/mcp.sh` (`sudo` efface `SSH_CONNECTION` ; adresse du journal, ADR 0024). Ne jamais déplacer cette logique dans un script du serveur exécuté avant `sudo` : les versions appartiennent à `cv`.
